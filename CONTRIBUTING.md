# Contributing

Thanks for your interest in contributing to `ts-utils`. This document explains how the repository is
organised and how to build, test, and run things locally.

## Repository structure

This repository is an npm workspaces monorepo. The root `package.json` declares two workspace globs:

```json
"workspaces": [
  "./packages/*",
  "./samples/*"
]
```

### `packages/*`

Each directory under `packages/` (currently `packages/array` and `packages/map`) is a published npm
package under the `@ts-utils` scope (`@ts-utils/array`, `@ts-utils/map`). A package contains:

- `src/` – the TypeScript source.
- `__tests__/` – Jest tests for the package.
- `dist/` – the built output (CJS, ESM, and UMD bundles plus type declarations), generated by `tsdown`
  and not committed to source control.
- `compatibility.js` – a plain Node script, run in CI, that `require`s the built package to catch
  packaging/compatibility regressions across Node versions.
- `package.json`, `tsconfig.json`, `tsdown.config.mts`, `jest.config.js` – per-package configuration.
- `README.md`, `CHANGELOG.md`, `LICENSE` – published alongside the package to npm.

### `samples/*`

Each directory under `samples/` (currently `samples/array` and `samples/map`) is a minimal, unpublished
(`"private": true`) demo app used to manually exercise the corresponding package. Each sample depends on
its package via `"@ts-utils/<name>": "*"`, which npm workspaces resolves to a symlink into
`node_modules/@ts-utils/<name>` pointing at the package in `packages/`. A sample contains:

- `index.html` – loads the package's UMD build directly with a `<script>` tag (e.g.
  `samples/array/index.html` loads `../../node_modules/@ts-utils/array/dist/array.umd.js`) and calls a
  handful of the package's functions, logging the results to the browser console.
- `index.js` – a Node script that does the same thing via `require("@ts-utils/<name>")` and logs the
  results to the terminal.

Because both entry points load the built `dist` output, the relevant package must be built before a
sample will work (see below).

## Building and testing locally

1. Install dependencies from the repository root (this also sets up the workspace symlinks used by the
   samples):

   ```sh
   npm install
   ```

2. Build all packages (runs `tsdown` for every workspace under `packages/*`):

   ```sh
   npm run build
   ```

3. Run the test suite (runs `jest --coverage` for every workspace under `packages/*`):

   ```sh
   npm test
   ```

4. Lint the repository:

   ```sh
   npm run lint
   ```

CI (see `.github/workflows/`) runs `npm run lint` (Lint), `npm test` across multiple Node versions
(Test), and `npm run build` followed by each package's `compatibility.js` across multiple Node versions
(Compatibility), so it's worth running all three locally before opening a PR.

If your change affects the public behaviour of a package, add a changeset so the release notes and
version bump are generated correctly:

```sh
npm run changeset
```

## Running a sample locally

Samples let you manually exercise a package in a browser or in Node after making changes.

1. Build the package the sample depends on (or run `npm run build` to build everything):

   ```sh
   npm run build
   ```

2. Then either:
   - **Browser**: open `samples/<name>/index.html` directly in a browser (e.g.
     `samples/array/index.html`). It loads the package's UMD build via a relative path into
     `node_modules`, so `npm install` must have already run to create that symlink, and the results are
     logged to the browser's developer console.
   - **Node**: run the sample's script directly:

     ```sh
     node samples/<name>/index.js
     ```

     e.g. `node samples/array/index.js`. This `require`s the package by name and logs the results to the
     terminal.

## Contribution flow

1. Create a branch named `type/issue-number`, where `type` is one of the
   [Conventional Commits](https://www.conventionalcommits.org/) types used in this repository (`feat`,
   `fix`, `build`, `ci`, `docs`, `refactor`, `test`, etc.) and `issue-number` is the number of the issue
   the change addresses, e.g. `feat/12`.
2. Make your changes, following the existing code style (enforced by ESLint/Prettier via `npm run
   lint`).
3. Write commit messages in Conventional Commits format (`type(scope): description`), where `scope` is
   the feature area affected (e.g. `array`, `map`) and can be omitted if the change spans multiple
   areas.
4. Before opening a pull request, make sure `npm run build`, `npm test`, and `npm run lint` all pass
   locally, and add a changeset (`npm run changeset`) if the change affects a package's published
   behaviour.
5. Open a pull request against `main` describing the change and referencing the issue it resolves.
